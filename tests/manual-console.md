# Manual console sign-off

In **Test bench → Storage verification suite**, the case selector shows each ID and name. Expand **Case descriptions and results** to see the action, expected output, and verdict reported by pytest. **All 70 cases** displays the entire catalog. **Full runner output** contains the original pytest log, including assertion failures and skip reasons.

To add a manual case, choose **My manual cases → New case**. Fill in the name, steps and expected output, then save it with **Not run**. Use the console to perform the steps. For custom file content, choose **Generate a test object → Create your own text file**, enter the filename and contents, and select **Prepare text upload**. When finished, reopen your saved case, enter the observed output, select **Passed** or **Failed**, and save again. Manual cases are stored on this browser and origin. Their verdicts are recorded by the tester and do not change the automated suite count.

Open [Objects](http://127.0.0.1:5173/#objects) and [Cluster](http://127.0.0.1:5173/#cluster) in separate tabs. Use a healthy four-worker cluster for the numbers below. These seven workflows take about ten minutes and use the running frontend. Each row gives you a visible pass criterion. Keep the 70-case Python run for physical inventories, concurrent clients, restarts and controlled faults.

| Check | Actions in the console | Screen output and pass criterion |
| --- | --- | --- |
| **1. Connection and workers** (TC-02/03) | Open **Cluster**, turn on **Auto-refresh**, and watch **Worker registry** for 10–15 seconds. | **Controller online**, four distinct worker names marked **Alive**, and heartbeat ages updating. A rising age for one worker over several refreshes merits investigation. |
| **2. Upload and inspect placement** (TC-09/10/19/26) | **Test bench → Generate a test object → 1 MiB + 1 byte → Prepare upload**. Enter `{"owner":"qa","run":1}` in **Custom metadata** and click **Upload object**. Copy the ID below the filename. | The upload banner reports **2 chunk(s) · HTTP 201**. Details show the custom keys. **Chunk placement** shows chunk 0 at **1 MiB** and chunk 1 at **1 B**. Both show **2 / 2 effective**, with two different worker names on each row. Worker assignments can vary. |
| **3. Change metadata and find the object again** (TC-11/12) | Record the object SHA-256. Apply `{"run":2,"reviewed":true}` in **Metadata patch**. Close the dialog and use **Objects → Find by ID** with the saved ID. | **Metadata updated · HTTP 200.** Reopened details show `owner: qa`, `run: 2`, and `reviewed: true`. ID, object SHA-256 and chunk IDs match the values before the edit. |
| **4. Verify a real download** (TC-07/16/62) | Upload a small local text file through **Objects → Upload object**. In its details click **Download & verify**. Save the download, then use **Test bench → Compare two files** with the original and the saved copy. Repeat the comparison with a different file. | The download reports **SHA-256 matched**. The comparison returns `match: true` and two equal hashes for the identical files, then `match: false` and different hashes for different contents. |
| **5. Empty object** (TC-23) | In **Test bench**, select **0 bytes**, prepare the upload, and upload it. Inspect the object and click **Download & verify**. | Upload returns **HTTP 201**, the chunk count is zero, and placement says **This object has no chunks.** Download reports **0 B · SHA-256 matched**. |
| **6. Error reporting and scrub** (TC-30/31/33 plus scrub controls) | In **Test bench → API error checks**, run **Missing upload file**, **Invalid metadata JSON**, and **Unknown object metadata** one at a time. Then click **Run scrub**. | The error panel shows expected and actual status **400, 400, 404** respectively, `passed: true`, and a readable JSON error. A successful scrub shows per-worker results and totals. On a healthy cluster `corrupt` and `lost` are zero. The checked count depends on all stored objects. |
| **7. Delete and verify absence** (TC-14/33) | Open the object from check 2 by its saved ID. Click **Delete object** and confirm. Refresh **Objects** and search for the same ID. Delete any other objects created for this walkthrough when finished. | **Deleted … · HTTP 204.** Its row disappears. Lookup reports **HTTP 404** and **object not found**. Other objects remain accessible. |

For a live recovery demonstration, keep the Cluster tab alongside the object details. On a disposable cluster, stop one worker holding a test replica from PowerShell, wait for **Dead**, click **Download & verify**, and use **Refresh placement** to watch the surviving copies. Start that worker again and wait for **Alive**. The automatic suite performs the underlying outage and repair checks.
